# План

## Текущий статус

Коротко: доменная модель и FSM раунда готовы и протестированы с самого
начала переписывания. С этой сессии дополнительно:

1. **Живой Postgres и S3 реально проверены** — раньше были только
   unit-тесты и моки границ (`CLAUDE.md` прямо называл это главным пробелом).
   Прогнана первая миграция, реальная регистрация/логин, реальная загрузка
   mp3 с извлечением ID3-тегов из настоящего S3-объекта.
2. **Найдены и исправлены два некосметических бага:**
   - отсутствие загрузки `.env` вообще (ни `dotenv`, ни `--env-file`) —
     переменные окружения из файла никогда не читались;
   - любая ошибка в `async` route-хендлере роняла весь процесс Node
     целиком (все игры во всех комнатах), а не только один запрос —
     воспроизведено и исправлено (`express-async-errors` + централизованный
     error-middleware).
3. **`apps/web` перестал быть пустым каталогом.** Минимальный, но реально
   работающий фронтенд: вход/регистрация, host-дэшборд с загрузкой треков,
   живой экран ведущего, живой экран игрока. Весь цикл игры (lobby → ... →
   finished, включая финальный раунд со ставкой) проверен и руками в
   браузере, и скриптом на `socket.io-client`.
4. **Добавлено разделение ролей хост/игрок на socket-слое** (`hostJoin`) —
   раньше его не было вовсе: любой подключённый сокет мог вызвать
   `startGame`/`advance`/`hostJudge`.

Подробности — в `shared.md`/`backend.md`/`frontend.md`.

## Известные пробелы, по приоритету

1. **Reconnect по токену.** Для пати-игры с телефонами по Wi-Fi разрывы
   соединения — это норма, не исключение. Сейчас разрыв просто помечает
   игрока `connected: false` навсегда, а повторный `joinRoom` после старта
   игры вообще отказывает (`"game has already started"`). Наша же демка в
   `apps/web` упирается в это при простой перезагрузке страницы. В старом
   `server/index.js` была рабочая версия reconnect-flow — стоит изучить
   перед реализацией новой.
2. **Waveform-редактор клипа (`wavesurfer.js`).** Был явно назван в
   стековых решениях с самого начала переписывания, но `DashboardView.vue`
   сейчас использует обычные числовые поля мс. Визуально выбирать клип по
   форме волны — то, ради чего частично затевалось переписывание UI.
3. **Командный режим end-to-end.** `transition.ts` уже умеет работать с
   `session.teams`/`teamMode` обобщённо, но нет socket API для создания
   команды или назначения туда игрока — `index.ts` всегда передаёт
   `playerId` напрямую как `contestantId`. Нужно: событие вроде
   `createTeam`/`joinTeam`, и резолюция `contestantId` в `index.ts` перед
   вызовом `gameManager.dispatch`.
4. **QR-код / короткая ссылка для входа.** Сейчас только ручной ввод кода
   комнаты на `/play`. Для реальной игры на большом экране полезен QR,
   который сразу открывает `/play?room=XXXXX`.
5. **Тесты на `apps/web`.** Сейчас 0 — ни unit, ни component. Минимум
   стоило бы покрыть `lib/api.ts` (особенно `uploadTrackFile`) и
   FSM-зависимые ветки рендера в `HostRoomView`/`PlayerView`.
6. **Проверка против реального прод-бакета (Cloudflare R2).** Presigned-
   логика идентична для любого S3-совместимого хранилища, и чек-сам-фикс в
   `s3Client.ts` важен именно для совместимости с R2/MinIO — но против
   настоящего R2 это никогда не гонялось, только против локального
   `adobe/s3mock`.

## Не горящее, но стоит держать в голове

- `GameSession` — только in-memory на процесс Node, без
  `@socket.io/redis-adapter`. Нормально для одного инстанса; станет
  проблемой при горизонтальном масштабировании.
- Тестовая фикстура `seed-track-1`, засеянная напрямую в БД через psql в
  самом начале (до того, как заработала настоящая загрузка) — можно
  удалить, больше не нужна для демонстрации.
- `docker-compose.yml` держит сервис `s3mock`, а не `minio`/`localstack` —
  если в будущем появится реальный повод вернуться к MinIO (например,
  нужна будет более точная эмуляция AWS-специфичного поведения), см.
  `backend.md` → «S3» про причину отказа от обоих.
